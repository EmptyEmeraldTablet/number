# 数列推理求解器

行测数字推理（找规律补数字）的自动求解器。核心思路不是"拟合一个公式"，而是**枚举「算子链 × 基础模式」的组合**，把原数列逐步变换到某个能识别的形态，再用规律复杂度排序给出可解释的候选答案。

```bash
npm install
npm run dev     # 打开 http://localhost:5173
npm test        # 跑 60 道题的回归测试
```

## 输入格式

整数、负数、分数 `1/2`、带分数 `1 1/2`、小数 `1.5`、根式 `√2` / `2√3` 都支持，用 `?` 标记空缺，逗号分隔。界面内置可折叠数字键盘，专门方便分数与根式的录入，并会在失焦时自动规范化格式（全角转半角、逗号统一、清理多余空格）。

## 为什么不是"多项式拟合"

给定 n 项总能找到 n−1 次多项式穿过所有点，但这毫无意义。行测题的真实结构是**两步走**：

```
原数列 --做差/做和/做商/拆分--> 中间数列 --> 基础规律（等差/质数/等比/递推）
```

所以求解器把"规律"拆成三层：

| 层 | 职责 | 例子 |
| --- | --- | --- |
| **算子 Op** | 一条数列 → 另一条数列，改变观察视角 | 做差、做和、做商、累加、奇偶位拆分、两两分组、数位和、开方 |
| **模式 Recognizer** | 在一条数列上判定基础规律并给出外推能力 | 常数、等差、等比、k 阶差分、质数、周期、幂次、1~3 阶线性递推、分数拆分、分组 |
| **搜索 Search** | 迭代加深枚举算子链（默认深度 2），每个中间状态都试一遍所有模式 | — |

## 三种求解路径

1. **选项模式** — 有选项时，每个选项填进去跑完整搜索，用"最佳规律的复杂度"给选项打分。准确率最高。
2. **外推模式** — 空缺在末尾时，先剥离空缺，在已知项上找规律并外推，再沿算子链**反向传播**回原数列（例如末端是"下一个差分"，要还原成"下一项"）。
3. **符号模式** — 空缺在中间时，把空缺当作符号 `x` 参与运算（仿射形式 `p·x + q`），由线性约束精确反解；多个空缺按从左到右逐个求解，每解一个序列就变长一项。

## 打分：为什么答案能排在第一位

```
score = Σ(算子代价) + 模式复杂度 + 支持项数惩罚 + 答案美观度惩罚
```

- 算子代价反映先验频率：做差 1.0、做和 1.4、做商 1.6、数位和 3.0；
- 递推类按**参数个数和数值大小**加罚（`aₙ = −aₙ₋₁ + 4aₙ₋₂ − 33` 这种丑陋参数会被压到后面）；
- 支持项数不足 4 项时重罚（3 个数凑等差数列属于弱证据）；
- 非整数、超大数适当扣分。

## 历史记录与失败案例收集

覆盖率靠一道道真实题目喂出来，所以每次求解都会自动存一条记录（`localStorage`），包含输入、选项、深度、候选答案、耗时、状态数，以及**求解器版本与规则集指纹**（如 `v0.3.0 · 18r/19o`）——后续改了规则集，也能分清哪些结果是旧版本产生的。

给记录填上正确答案后会自动判定：

| 状态 | 含义 |
| --- | --- |
| ✓ 答对 | 正确答案出现在候选里（记下命中名次） |
| ✗ 答错 | 候选非空，但都不等于正确答案 |
| ? 未解 | 候选为空，求解器什么都没找到 |
| · 待核对 | 还没填正确答案 |

两种导出：

- **导出 JSON**：完整快照，带 `summary` 统计和每条用例的候选、规律名、耗时、版本，适合留档或做分析；
- **导出用例**：只导出「答错」和「未解」且已标注答案的题，生成可直接粘进 `tests/run.ts` 的 `{ name, input, expect, opts }` 数组——这是修复覆盖率的主循环：做题 → 标注 → 导出 → 补测试 → 改规则。

同一道题反复求解只保留最新一条，已标注的答案不会被覆盖。

## 覆盖范围

见界面底部「规律清单」。已完整支持：多级差分、做和/做商/做积、质数与合数、幂次及幂次修正、周期、交叉与分组、分数拆分数列、1~3 阶线性递推、隔项递推、因式分解（双因子各自成规律）、阶乘、数位和、按位拆分、数位等式、**根式数列**（`a·√b` 与 `√n` 两种口径）、**小数整数/小数部分分列**。

**已知限制**：对数数列、图形数阵、四项及以上递推、幂次 ± 等差修正尚未实现；反约分只做了常见情形。

### 数位类是怎么处理的

位数相同的多位数（四位数、三位数）在行测里几乎不参与大数运算，而是**按字符串处理**——把各位拆开看成独立的数字。因此引擎对这类题有专门的通道：

- **按位拆分**：各位独立成列，每列各自成规律（`12, 23, 34, 45` → 十位等差、个位等差）；
- **数位等式**：把各位分成两组，组内运算后相等（`2675` → `2×6 = 7+5 = 12`）。

数位等式的枚举维度是「分组位置 × 左聚合 × 右聚合」，聚合包括和、积、差、绝对差、平方和，分组包括连续二分与首尾一组。

这类规律有个特殊性质：**答案不唯一**。`a×b = c+d` 对任意四位数都可能成立，满足条件的数有无穷多个，所以它无法外推，只能靠选项筛选。引擎的处理是：给了选项就逐个验证（正确选项会以极低复杂度胜出）；没给选项时保留普通规律的解，但会给出显眼的黄色警告——「这些数存在数位规律：…，满足条件的答案不唯一，下方结果多半是巧合拟合」。

同时，**周期规律在四位数序列上会被降权**（+1.6 复杂度）。因为四位数考"周期循环"的概率极低，考的是数位关系；不降权的话，周期拟合会以更低的成本把正确答案挤下去。

### 因式分解型是怎么处理的

像 `1, 18, 75, 245, 567, 1331` = `1×1, 2×9, 3×25, 5×49, 7×81, 11×121`，即「质数 × 奇数平方」。

难点在于**每项的分解方式不唯一**（567 可以是 7×81，也可以是 9×63、21×27），必须找到一个分解让两条因子序列同时规整。做法是：

1. 对每项枚举因子对 `(a, b)` 且 `a ≤ b`；
2. 枚举前 4 项的因子对组合（用组合数上限剪枝）；
3. 每组用 `simpleExtrap` 分别拟合两条因子序列，再**在线验证**第 5 项以后——预测出的 `(a, b)` 必须真的出现在该项的因子对里，否则立刻剪掉；
4. 全部通过才算命中，外推时两因子相乘。

两个必须处理的细节：`1` 不是质数，但这里的第一因子序列 `1, 2, 3, 5, 7, 11` 实质是"1 打头的质数"，所以 `simpleExtrap` 专门加了这一模式；同时顺序上让它排在等差之后，否则 `1, 3, 5, 7` 会被误判成质数而不是公差 2 的等差。

### 根式与小数是怎么处理的

- 根式：解析时同时保留「化简后的系数」和「原始根号内数字」。口径 A 统一化简成 `a·√b` 后对系数 `a` 求规律（`√2, √8, √18` → `5√2`）；口径 B 要求书写系数恒定、对根号内的数求规律（`√2, √5, √8, √11` → `√14`）。两条口径的结果一起参与打分。
- 小数：拆成整数部分与小数部分两条序列分别求解，再按「拼接」语义合并（小数部分 `11` 拼成 `.11`，因此 `1.1, 2.2, 4.4, 7.7` → `11.11`）。同时保留整体规律的候选一起排序；若整数部分全同（如 `0.1, 0.2, 0.4, 0.8`），说明拆分没有信息量，直接交给整体规律处理。

## 部署到 Cloudflare Pages

纯静态站点，没有服务端依赖、没有环境变量、没有外部 API。

| 配置项 | 值 |
| --- | --- |
| 框架预设 | Vite（或选 None） |
| 构建命令 | `npm run build` |
| 输出目录 | `dist` |
| Node 版本 | `20`（见 `.nvmrc`，也可在环境变量里设 `NODE_VERSION=20`） |

**方式一：连接 Git 仓库（推荐）**

推送到 GitHub/GitLab 后，在 Cloudflare Pages 里「连接到 Git」，按上表填构建配置即可，之后每次 push 自动部署。

**方式二：命令行直接上传**

```bash
npm run build
npx wrangler pages deploy dist --project-name gwy-number-solver
```

**几个注意点**

- 不要给项目设置 `NODE_ENV=production` 环境变量——那会让 `npm install` 跳过 devDependencies，而构建里的 `tsc --noEmit` 依赖 `typescript`。若确实需要精简依赖，把构建命令换成 `npm run build:fast`（纯 `vite build`，不做类型检查）。
- 单页应用、没有前端路由，不需要 `_redirects`。
- `public/_headers` 会在部署时生效：带 hash 的 `/assets/*` 长缓存一年，入口 HTML 不缓存，另附两个基础安全头。
- 产物只有 3 个文件、gzip 后约 65 kB，远低于 Pages 的单文件 25 MB 限制。
